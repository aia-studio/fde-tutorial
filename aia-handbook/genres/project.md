# genre: project · 项目实战

> 覆盖层。只写与 `_core.md` 不同的部分。
> 适用：围绕一条真实交付链路，从需求到上线走一遍。读者目标是「照着走完一次」。

## 1. 判定标准

选 `project` 的标志：

- 章节按**时间线/阶段**推进，不是按知识点
- 每一章结束时，项目本身要变一个样（多一个模块、过一个验收）
- 读者读完的产物是「一个能演示的系统 + 一套交付文档」

如果章节之间可以任意调换顺序，那不是这本书，是 `practical`。

## 2. 章节骨架（排他 · 主类型决定）

```
① 阶段头块（引用块）
   > 本阶段：<项目推进到哪一步>
   > 前置：ChNN <上一阶段>｜工期：<人天>｜交付物：<可验收的东西>
   > 阶段目标：<一句话>
② 阶段全景图（项目整体进度条 + 本阶段高亮）
③ 现场开场（≤10 行：这次是谁提了什么要求，为什么现在必须做）
④ 正文各节（4–6 节，每节按「决策 → 实施 → 验证」组织）
⑤ 阶段交付物清单（表格：交付物 / 验收标准 / 谁来验收）
⑥ 复盘（做对了什么 / 做错了什么 / 下次怎么改，三段各 ≤5 行）
⑦ 风险登记（本阶段新识别的风险 + 已关闭的风险，表格）
⑧ 下一阶段（衔接，说明为什么下一步是这个）
```

第 ④ 段的「决策 → 实施 → 验证」是这一类的核心结构：
**先讲当时为什么这么选，再讲怎么做的，最后讲怎么确认做对了。**
跳过「决策」就变成操作手册，跳过「验证」就变成流水账。

## 3. 标注体系

| 标注 | 用途 |
| --- | --- |
| 【现场故事】 | 客户/同事的原话、真实反应（虚构但可信） |
| 【风险】 | 可能导致返工或验收失败的因素 |
| 【取舍】 | 两个方案里为什么选这个，放弃了什么 |
| 【返工】 | 做错了、推翻重来的地方，以及原因 |
| 【验收】 | 客户/甲方会怎么判断这个交付物合格 |
| 【代价】 | 这个选择的成本与副作用 |
| 【待确认】 | 需求或行业做法存在分歧，并列给出 |
| 【排查】 | 出问题时的诊断顺序 |

【返工】是这一类最重要的标注。**只写顺利路径的项目书没有价值**——
读者真正需要的是「哪里会翻车、翻车后怎么回来」。

## 4. 与 practical 的区别（两边都别混）

| 维度 | practical | project |
| --- | --- | --- |
| 组织维度 | 知识点 | 时间线/阶段 |
| 章节可换序 | 基本可以 | 不可以，换了就断 |
| 骨架第一段 | 本章解决什么问题 | 本阶段推进到哪一步 |
| 收尾 | 练习 + 常见坑 | 交付物验收 + 复盘 + 风险登记 |
| 代码范围 | 本章示例 | 整个项目的一个切片，必须能与前阶段拼起来 |

**判据一句话：** 读者能不能只挑第 7 章看？能，是 practical；不能，是 project。

## 5. 代码要求

- 每阶段代码必须能接上前一阶段的产物，**不能推倒重来**
- 阶段末必须有可运行快照（对应 `capstone/chNN` tag）
- 工程结构完整：`app/` `tests/` `deploy/` `config/`，不是单文件脚本
- 每个阶段至少一个测试，且测试要能跑
- 部署相关章节必须给 `docker-compose.yml` 或等价物

## 6. 图表要求

- ≥2 张图：1 张阶段全景 + ≥1 张架构/时序/ER
- ≥1 张表：交付物清单或风险登记
- 阶段全景图必须标出**已完成 / 本阶段 / 未开始**三种状态

## 7. 练习要求

不叫「练习」，叫「里程碑任务」：

| 项 | 要求 |
| --- | --- |
| 形式 | 交付物，不是题目 |
| 验收 | 必须写清「谁来验、按什么标准验」 |
| 难度 | 与本章阶段难度一致，不设挑战题 |

## 8. 反模式（这一类特有）

| 禁止 | 原因 |
| --- | --- |
| 玩具项目（Todo List、博客系统） | 没有真实约束，学不到交付 |
| 无验收标准的交付物 | 读者不知道自己做对没有 |
| 只讲顺利路径，不写返工 | 真实项目一半时间在返工 |
| 每章项目推倒重来 | 读者拿不到累积成果 |
| 需求章节写成「用户说要一个 X」 | 真需求要经过澄清与取舍 |
| 时间线跳跃（跳过联调、跳过上线） | 跳过的正是最容易出事的部分 |
