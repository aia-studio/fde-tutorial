## 反直觉开场

一个团队加了 BM25 之后，整体召回率没升，长查询反而下降。他们以为是权重没调好，试了七组参数都不行。真正的原因是两类检索返回的候选高度重叠，融合只是把同一批结果换了顺序。

### 2.1 两种融合方式

> 路径：必读

RRF 只看排名，不看分数；加权求和把两路分数直接相加。分数尺度不一致时，加权求和会把一路的声音放大。

| 方式 | 输入 | 代价 | 适用条件 |
| --- | --- | --- | --- |
| RRF | 排名 | 丢掉分数强弱 | 两路分数不可比 |
| 加权求和 | 分数 | 需要归一化 | 两路分数同尺度 |

### 2.2 权重从哪来

> 路径：必读

权重不该拍脑袋。先固定评测集，再按查询类型分层看召回，最后才调权重。没有分层，一个总分会把两类失败互相抵消。

```python
def rrf(rankings: list[list[str]], k: int = 60) -> list[str]:
    score: dict[str, float] = {}
    for ranking in rankings:
        for pos, doc in enumerate(ranking, 1):
            score[doc] = score.get(doc, 0) + 1 / (k + pos)
    return sorted(score, key=score.get, reverse=True)
```

### 2.3 什么时候不该混合

> 路径：选读

如果两路候选重叠超过八成，融合的增量很小。这时更该做的是改切分或补字段，而不是继续调权重。

| 现象 | 说明 | 该做什么 |
| --- | --- | --- |
| 候选重叠八成 | 两路在找同一批文档 | 改切分或补字段 |
| 长查询变差 | 关键词噪声压过语义 | 按查询长度分层 |
| 短查询变差 | 语义泛化压过字面 | 提高关键词权重 |

### 2.4 评测顺序

> 路径：必读

先看数据是否覆盖失败类型，再看召回，最后看排序。顺序反了，会把数据问题误判成算法问题。

| 步骤 | 看什么 | 判据 |
| --- | --- | --- |
| 一 | 评测集覆盖 | 三类失效都有样本 |
| 二 | 召回 | 每类分别算 |
| 三 | 融合后排序 | 不只看总分 |

【代价】按查询类型分层评测要维护更多标注，但它能告诉你「哪一类变差」，总分不能。

## 权衡表

| 方案 | 代价 | 适用条件 |
| --- | --- | --- |
| 固定权重 | 换语料就失效 | 查询类型单一 |
| 分类分层 | 维护成本高 | 查询类型差异大 |
| 不混合 | 专有名词漏召 | 语料口语化 |

## 失效边界

- 评测集不覆盖专有名词时，混合的收益无法被看见。
- 两路候选高度重叠时，融合只是在重排同一批结果。
- 查询长度分布单一，分层权重会过拟合。
