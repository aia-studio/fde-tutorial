# ch07 多轮对话与上下文

前置：`data/index.db` 已建好（见 ch02），`data/eval/questions.jsonl` 已有二十题（见 ch06）。
本章代码复用 ch06 评测里跑的那条链路，不另起一套。

```bash
cd src
python -m ch07.rewrite      # 改写规则，纯规则不查库
python -m ch07.pipeline     # 三轮会话，对比带状态与不带状态
python -m ch07.eval_multi   # 三条会话逐轮评测
```

`ch07.rewrite` 实测输出：

```text
用户问               带状态                       动作          空状态
它保修多久             A100 显卡保修多久               还原「它」       它保修多久
保修期多久             A100 显卡 保修期多久             补产品         保修期多久
显卡风扇保修吗           A100 显卡风扇保修吗              补型号         显卡风扇保修吗
那换屏要钱吗            A100 显卡 换屏要钱吗             去语气词+补产品    那换屏要钱吗
A100 的发票丢了怎么办     A100 的发票丢了怎么办                         A100 的发票丢了怎么办
你们支持比特币付款吗        A100 显卡 你们支持比特币付款吗        补产品         你们支持比特币付款吗
```

最后一行是这套规则已知的缺陷：范围外的问题也被硬拽进本产品。
改写之前先做一次范围判断，超范围直接走拒答，不要进改写。

`ch07.pipeline` 实测输出：

```text
轮次      用户问         改写后                   动作      工单      状态/全量字符
第 1 轮  显卡花屏出现彩色条纹  显卡花屏出现彩色条纹            不改写     T-1007  16/46
第 2 轮  保修期多久       A100 显卡 保修期多久         补产品     T-1026  27/89
第 3 轮  显卡风扇保修吗     A100 显卡风扇保修吗          补型号     T-1026  40/134

状态字段 product=A100 显卡 last_ticket=T-1026
同三句各问各的：
  显卡花屏出现彩色条纹  → T-1007
```

第三轮最能说明问题：不带状态时，系统按 Ch04 的规则要求「补充型号」；
带上状态，上一轮已知的 A100 直接补进去，这一轮就能答。

`ch07.eval_multi` 实测输出：

```text
无状态：答对 4/9　前五命中 9/9　误拒 2/9　会话通过 0/3
有状态：答对 7/9　前五命中 9/9　误拒 2/9　会话通过 2/3

案例    轮   用户问           名次    答对    拒答
M1    1   显卡花屏出现彩色条纹    1     是     否
M1    2   保修期多久         1     是     否
M1    3   显卡风扇保修吗       1     是     否
M2    1   显示器黑屏但电源灯亮着   1     是     否
M2    2   保修期多久         1     否     是
M2    3   换屏要钱吗         3     否     是

M3    2   保修期多久         1     是     否

```

前五名命中两种模式都是 9/9，说明候选一直够用，差别在排序与拒答。
M2 的两轮是改写的副作用：把「HY-100 显示器」拼进查询串后，
两条保修口径不同的工单同时进前五，Ch04 的冲突规则直接拒答。
会话层没有变差，是改写方式不对——产品名应该当过滤条件，而不是拼进查询串。

样本只有九轮，涨几条只能看方向。要拿它做验收，先扩到三十轮以上。
