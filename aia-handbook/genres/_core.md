# 写作宪法 · 核心层

> 所有 genre 共有。加载顺序：`_core.md` → `genres/<genre>.md` → `genres/<genre>.yaml` → 书级 override
> 后者覆盖前者。**本层只写与书类无关的规则**，凡是「取决于你写什么书」的，一律下沉到 genre 层。

## 1. 语体

| 项 | 规定 |
| --- | --- |
| 人称 | 第二人称「你」称呼读者；作者与读者一起做事时用「我们」。**禁用**「大家」「各位同学」「笔者」「本文」「本教程」 |
| 时态视角 | 现在时为主（「你要做的是……」）；讲历史用过去时 |
| 语气 | 直接、诚实、可执行。**允许泼冷水**——「这个需求不该接」「这类场景别用 Agent」。禁止鸡汤、成功学、恐吓式营销 |
| 句子 | 单句 ≤ 40 字，一句话只讲一个判断 |
| 段落 | 每段 ≤ 4 行（屏幕约 100 字），一段只讲一个意思。技术密度高的段可到 6 行，但连续两段超过就必须拆 |
| 每节开头 | 第一句必须回答「这一节解决什么问题」，不用悬念式铺垫 |
| 每节结尾 | 一段小结（≤3 句）+ 一句「你应该能回答的问题」（把知识变成自测） |

**禁用空词**：综上所述、由此可见、众所周知、不言而喻、赋能、闭环、抓手、底层逻辑、
颗粒度、打通、拉齐。这些词出现时，作者通常还没想清楚要说什么。

## 2. 事实纪律

1. 任何数字（比例、金额、耗时、规模、性能）必须在 `claims.jsonl` 登记
   `source` + `date` + 口径。**没有出处的数字不许出现在正文。**
2. 时效性数据（薪酬、市场规模、版本号、榜单）加一句「以阅读时最新公开数据为准」。
3. 法规与合规：只讲「要做什么、找谁确认」，**不提供法律意见**，不编造条文。
4. 行业存在分歧的结论：给主流说法 + 【待确认】并列 + 适用条件区分，**不站队**。
5. 不编造精确统计。写「多数团队反映」可以，写「73.6% 的团队」需要出处。

## 3. 术语纪律

- 首次出现：`中文全称（English Full Name，缩写）`；之后统一用最简形式（优先缩写）
- 全书同一概念只能有一个名字。换成同义词即视为错误，闸门会查
- 只能使用 `glossary.json` 已登记的术语。要造新词必须登记，**不得为已有概念另起名**
- 核心术语总数不超过 `book.yaml` 的 `max_core_terms`。超了说明概念没收敛

## 4. 通用反模式（任何 genre 都禁止）

| 禁止 | 原因 |
| --- | --- |
| 只讲概念不给可操作步骤 | 读者读完不会做 |
| 代码块没有文件路径与运行命令 | 读者无法复现 |
| 正文贴大段完整代码 | 书稿会变成仓库的复制品 |
| 大段 API 文档式罗列 | 应改为「这个参数在什么场景下要改」 |
| 用「很简单」「显而易见」「只要……就」 | 对读者是打击，且通常是作者自己没想清楚 |
| 只写成功案例 | 真实价值在踩坑与取舍 |
| 结论没有代价说明 | 每个技术选择都要讲原因和代价 |
| 图只是装饰 | 每张图必须承担一个信息职责 |
| 硬编码编号式交叉引用（「见第 3 章第 5 节」） | 编号会变，只写到 `ChNN` 这一级 |
| 术语同义替换 | 破坏全书一致性 |
| 编造实测输出 | 跑不出来就写「本章示例未验证」，不许伪造 |

## 5. 标注的使用原则

标注体系的具体种类由 genre 定义。使用原则是通用的：

- 标注写的是**读者会踩的坑**，不是作者想强调的话
- 每节标注 ≤ 2 处，一章 ≤ 8 处。超了说明重点不突出
- 同一条信息只用一种标注，不得用两种重复
- 标注必须紧跟它所修饰的段落，不跨段、不放章末
- 标注内容必须具体可执行。「注意安全」不合格，「客户内网无外网时 pip 必须走离线 wheel」合格

## 6. 与读者的关系

- 不假设读者记得前文。要引用前置概念时，用一句话复述，再给 `ChNN` 链接
- 不贬低读者，也不抬高作者。「我当时也踩了这个坑」可以，「这么简单都不会」不行
- 每章至少一处承认不确定性。技术写作没有全知视角，装全知反而不可信
