# genre: practical · 技术实战手册

> 覆盖层。只写与 `_core.md` 不同的部分和 genre 特有的段落。
> 适用：框架、工具链、工程实践。读者目标是「读完能自己动手做出来」。

## 1. 这一类的判定标准

选 `practical` 的标志：

- 读者读完的动作是「打开编辑器开始写」，不是「理解了某个原理」
- 技术会随版本变化，所以需要写明版本
- 有明确的对错：代码能跑 / 跑不起来

如果你的书读者读完主要是「能判断该不该用」，那是 `principle`，不是这本。

## 2. 章节骨架（排他 · 主类型决定）

```
① 章首页头块
   > 本章解决：<一句话问题>
   > 前置：ChNN <必须读过的章>
   > 阅读 40 分钟｜动手 2 小时｜交付物：<能跑出什么>
② 章首导图（Mermaid mindmap，展示本章结构）
③ 场景开场（≤10 行，一个具体的人遇到的具体问题，不含解决方案）
④ 正文各节（4–6 节）
⑤ 章末小结表（要点 / 一句话结论 / 与前文的关系）
⑥ 动手练习（2–4 题，递进，每题给验收标准）
⑦ 自查清单（≤10 条，勾选项，可打印）
⑧ 常见坑（3–5 条，格式：现象 → 原因 → 怎么办）
⑨ 下一章（1–2 句，衔接真实存在的下一章）
```

第 ③ 段是最容易被写坏的一段。**场景开场只描述问题，不给答案**，
而且必须是一个具体的人在一个具体场景里——「某公司的工程师」不算具体。

## 3. 标注体系（排他 · 主类型决定）

只用这 8 种，方括号前缀：

| 标注 | 用途 |
| --- | --- |
| 【注意】 | 会导致返工或事故的硬约束 |
| 【提示】 | 提高效率的小技巧 |
| 【陷阱】 | 常见错误及其后果 |
| 【最佳实践】 | 行业已形成共识的做法 |
| 【代价】 | 该选择的成本与副作用 |
| 【待确认】 | 行业有分歧，并列给出，不站队 |
| 【版本】 | 版本差异，会影响读者能不能跑通 |
| 【排查】 | 出问题时的诊断顺序 |

【代价】和【排查】是这一类书的核心：前者防止读者以为有免费午餐，
后者决定读者卡住时能不能自救。一章里这两个至少各出现一次（除纯概念章）。

## 4. 代码要求

- **凡出现在正文的代码，必须能跑。** 不能跑的示例放 `src/` 也要标注「示意，未验证」
- 片段 ≤ 30 行（`book.yaml` 的 `code_block_max_lines`）。超了就拆或放 `src/`
- 每段代码给出：文件路径 → 运行命令 → 实测输出。**输出必须是真跑出来的**
- 省略处写 `# ... 完整代码见 src/chNN/xxx.py`，不许只写「此处省略」
- 错误示例可以出现，但标题必须写 `❌ 错误写法`，并在下方给 `✅ 正确写法`
- 密钥一律占位符（`sk-xxx` / `your-api-key` / `<客户域名>`）
- 无外部依赖能跑就无依赖。必须有第三方库时，在 README 写清安装方式

## 5. 图表要求

- ≥2 张图：1 张章首导图 + ≥1 张链路/时序/架构图
- ≥1 张表
- **≥1 张图必须服务于「读者要动手做的事」**——链路图、部署图、时序图
- 图只讲一件事，节点 ≤ 12 个

## 6. 练习要求

2–4 题，难度递进：

| 类型 | 要求 |
| --- | --- |
| 照做 | 给定输入，跑出给定结果 |
| 改一改 | 改一个参数或条件，观察变化并解释 |
| 自己设计 | 给定约束，自己选方案 |
| 挑战 | 跨章综合，或处理边界情况 |

**每题必须给验收标准，且标准必须可观察。**
「理解了 RAG 的流程」不合格；「你的问答服务返回的 3 条答案都带原文页码」合格。

## 7. 反模式补充（这一类特有）

| 禁止 | 原因 |
| --- | --- |
| 讲完原理不落步骤 | 读者知道「为什么」但不知道「怎么做」 |
| 步骤不可执行（缺前置条件、缺命令、缺路径） | 读者卡在第一步 |
| 示例数据不可得 | 代码能跑但没数据，等于不能跑 |
| 只给最终代码，不给演进过程 | 读者看不懂为什么长成这样 |
| 版本无关地讲 API | 半年后读者按书操作直接报错 |
| 一次讲三个方案却不给选择依据 | 读者更困惑了 |
