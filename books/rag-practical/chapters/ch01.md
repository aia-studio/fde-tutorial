# Ch01 跑通最小链路

> 本章解决：怎么在半小时内让问题进、答案出？
> 前置：无｜阅读 40 分钟｜动手 2 小时｜交付物：能返回答案的最小服务

## 场景开场

周一上午，客服主管把一份表格发到群里。表格里有三百条历史工单。她说同事每天要翻半小时，才能找到相似问题的处理办法。你手上只有一台装了 Python 的笔记本，没有向量库，也没有标注数据。这一章要做的不是效果，而是先把路走通。

### 1.1 先定「最小可用」的边界

> 路径：必读

最小可用不是功能少，而是端到端跑通。问题进去，答案出来，中间不断链。功能可以后加，路必须先通。

判断标准只有一条：拿一条真实工单，能不能跑出带原文的结果。

先把不做的写下来，防止范围膨胀。

| 能力 | 最小实现 | 这一章先不做 |
| --- | --- | --- |
| 读数据 | 读一个 csv | 接数据库 |
| 找相似 | 关键词包含 | 向量检索 |
| 出答案 | 拼原文片段 | 调大模型 |
| 引用 | 打印工单号 | 可点击链接 |

这张表还有一个作用：它就是你跟主管对齐范围的依据。她如果问「为什么不能直接回答」，你指着「先不做」那一列解释。

还有一种常见误解：把「先不做」理解成「以后也不做」。这张表只约束第一版。后面几章会逐项替换：关键词换成向量，拼原文换成模型生成，工单号换成可点击引用。范围是暂时的，不是永久的。

把边界写下来还有一个作用：后面每次有人提新需求，你可以先问「这属于哪一版」。不属于第一版的，记到待办，不塞进当前迭代。项目失控往往不是技术问题，是范围没有纸面约束。

### 1.2 搭一个能返回答案的骨架

> 路径：必读

先写入口，再填细节。入口能跑，后面每一步都有地方放。骨架不需要正确，只需要能被调用。

入口函数只做三件事：读数据、找一条、返回原文。参数与返回值先定下来，内部可以返回空。

```python
def answer(question: str, rows: list[dict]) -> dict:
    hits = [r for r in rows if question[:2] in r["description"]]
    if not hits:
        return {"answer": "", "source": ""}
    top = hits[0]
    return {"answer": top["description"], "source": top["ticket_no"]}
```

【注意】不要在这一步引入大模型。模型会掩盖链路问题，让你分不清是检索错了还是生成错了。骨架跑通之后，再决定哪一步换成模型。

函数签名先定下来，有个额外好处：Ch03 换成向量检索时，只要保持参数与返回值不变，调用方一行都不用改。接口稳定，内部随便换，这是后面几章能连续迭代的前提。

不要过早抽象。这一章不需要「引擎」「管线」「工厂」这些概念。一个函数能跑通，就先用一个函数。抽象等到第二次重复时再做，否则你会先花两小时设计，再花两小时删掉。

骨架跑通后，把它固化成一个命令。每次改完都跑同一条命令，输出一致才算没退化。这比记住「上次好像能跑」可靠。命令写进 README，换一台机器也能复现。

### 1.3 用样例工单跑通

> 路径：选读

样例数据要能代表真实分布。至少包含三类：专有名词、数字、口语化描述。只准备一类，你会误以为链路很稳。三类各留一条，后面做召回评估时可以直接复用。

读取时先试 utf-8-sig，失败再换 gbk。老系统导出的文件多半带 BOM，直接用 utf-8 会读出乱码。

```python
import csv

def load(path: str) -> list[dict]:
    for enc in ("utf-8-sig", "gbk"):
        try:
            with open(path, encoding=enc) as f:
                return list(csv.DictReader(f))
        except UnicodeDecodeError:
            continue
    raise ValueError("编码不支持")
```

如果两种编码都失败，不要猜。用 `file` 命令或十六进制查看前几个字节，确认是不是 UTF-16 或 GB18030。猜编码会浪费半小时，查字节只要一分钟。

| 检查项 | 通过标准 | 常见失败 |
| --- | --- | --- |
| 能读 | 打印前三条不报错 | 编码错 |
| 能找 | 至少命中一条 | 关键词太窄 |
| 能答 | 输出含原文句子 | 只返回空串 |

「能答」这一项最容易被放过。空字符串说明匹配到了但没取到正文，这属于半通不通。半通比不通更危险，因为你以为它好了。

### 1.4 定义第一版验收标准

> 路径：必读

验收标准要能被客户指着屏幕确认。写「回答准确」没用，写「十条工单里八条返回原文片段」才有用。

第一版只承诺一条链路，不承诺准确率。准确率是后面五章的事。

| 验收项 | 标准 | 谁来确认 |
| --- | --- | --- |
| 能读 | 三百条工单全部读入 | 你 |
| 能找 | 十条测试工单命中八条 | 客服主管 |
| 能答 | 命中时返回原文片段 | 客服主管 |
| 能追溯 | 每条答案带工单号 | 你 |

验收人也要写清楚。写「客户确认」等于没写，写「客服主管在演示现场确认」才有约束力。谁签字，谁就要到场；不到场就顺延，不要替他做判断。

验收演示建议控制在五分钟：两分钟讲范围，两分钟跑三条工单，一分钟说下一版做什么。演示里一定要留一条查不到的样本，让客户看到系统会说「不知道」。这比多跑十条成功样本更能建立信任。

验收标准不要只写在聊天记录里。写进仓库的 README 或 issue，下次客户换人时，标准还在。标准一旦写下就冻结，要改必须双方确认并记录原因。

【代价】把标准定得低，第一版容易过，但后面每加一个能力都要重新谈验收。把标准定得高，第一版过不了，项目会卡在演示阶段。经验做法是先定「能跑通」，再定「跑得准」。

## 本章小结

| 要点 | 结论 |
| --- | --- |
| 最小可用 | 端到端跑通，不是功能少 |
| 骨架先行 | 入口能调用，细节才有地方放 |
| 半通不通 | 比完全不通更难发现 |
| 验收标准 | 要能被指着屏幕确认 |
| 范围 | 先不做不等于以后不做 |

## 动手练习

1. 用三条工单跑通骨架，确认返回原文片段。验收：终端打印出工单号与原文。
2. 把关键词匹配换成「描述包含问题前四个字」，观察命中变化。验收：记录命中数变化并解释。
3. 故意传一个空问题，观察返回。验收：不抛异常，返回空结果。

## 常见坑

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| 乱码 | 编码不对 | 先 utf-8-sig，再 gbk |
| 空结果 | 关键词太窄 | 截取问题前几个字 |
| 有结果但没原文 | 只取了 id | 返回 description |
| 演示时快，换数据就慢 | 数据量变大 | 先记录耗时，Ch03 再优化 |
| 演示全成功 | 客户以为不会错 | 留一条查不到的样本 |
