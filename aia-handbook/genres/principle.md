# genre: principle · 原理与设计

> 覆盖层。只写与 `_core.md` 不同的部分。
> 适用：讲清一套机制怎么运作、为什么这样设计、什么时候会失效。
> 读者目标是「能判断该不该用、为什么」。

## 1. 判定标准

选 `principle` 的标志：

- 读者读完的动作是「做出一个判断」，不是「敲一段代码」
- 技术可能十年不变，所以不需要锁版本
- 有反直觉之处：外行会猜错，内行也常说不清

如果读者读完要打开编辑器动手，那是 `practical`。

## 2. 章节骨架（排他 · 主类型决定）

```
① 问题头块（引用块）
   > 本章回答：<一个可以用一句话说清的问题>
   > 前置：ChNN <需要的概念>｜预计 50 分钟
   > 读完你能判断：<一个具体的决策>
② 概念地图（本章概念在整体机制里的位置，与相邻概念的关系）
③ 反直觉开场（≤10 行：一个失败案例，或一个「按理说不该这样」的现象）
④ 正文各节（4–6 节，逐层拆解机制）
⑤ 权衡表（可选方案 / 各自代价 / 适用条件）
⑥ 失效边界（这套机制在什么条件下不成立，3–5 条）
⑦ 延伸阅读（2–3 篇，每篇一句「为什么值得读」）
⑧ 下一章（1–2 句）
```

第 ⑥ 段是这一类不可省略的一段。**没有边界的原理不是原理，是信仰。**

第 ③ 段必须是反直觉的。如果开场现象是「大家都觉得这样不好，果然不好」，
那这章没有存在价值——直接删。

## 3. 标注体系

| 标注 | 用途 |
| --- | --- |
| 【前提】 | 这条结论成立所依赖的假设 |
| 【争议】 | 学界/业界尚未定论的分歧 |
| 【边界】 | 机制失效或不适用的条件 |
| 【反例】 | 看起来适用、实际不适用的场景 |
| 【推导】 | 关键推理步骤，读者会卡住的地方 |
| 【代价】 | 该设计换来的东西与付出的东西 |
| 【常见误解】 | 广泛流传但错误的理解，附纠正 |
| 【待确认】 | 无定论且无法用【争议】归类的 |

【常见误解】是这一类最有效的标注。**先立一个错，再拆它**，
比平铺直叙讲一遍正确的东西记得牢。

## 4. 与 practical 的区别

| 维度 | practical | principle |
| --- | --- | --- |
| 读者产出 | 能跑的东西 | 能做判断 |
| 骨架第 5 段 | 小结表 | 权衡表 |
| 骨架第 6 段 | 动手练习 | 失效边界 |
| 代码占比 | 高 | 低，伪码优先 |
| 版本敏感 | 高 | 低 |
| 收尾 | 常见坑 | 延伸阅读 |

**判据一句话：** 删掉所有代码，这章还成立吗？成立是 principle，不成立是 practical。

## 5. 代码要求

- 代码是佐证，不是主体。**能用手写伪码就不用真代码**
- 需要真代码时，只给关键函数签名与调用顺序，不给完整实现
- 伪码用 ```text 包裹，不用具体语言语法
- 不要求可运行（`code_required: false`），但要求逻辑正确

## 6. 图表要求

- ≥2 张图：1 张概念地图 + ≥1 张机制图（状态流转 / 数据流 / 时序）
- ≥1 张表：权衡表或对比表
- 机制图优先于流程图——流程讲「先后」，机制讲「为什么这样」

## 7. 练习要求

| 类型 | 要求 |
| --- | --- |
| 推导 | 给定前提，补全推理链的中间步骤 |
| 判断 | 给 3 个场景，判断该用哪种机制，写明理由与代价 |
| 找错 | 给一段错误论断，指出错在哪条前提上 |

**不给「实现题」。** 这一类书的练习考的是判断力，不是编码速度。

## 8. 反模式（这一类特有）

| 禁止 | 原因 |
| --- | --- |
| 只给结论不给推导 | 读者只能背，不能迁移 |
| 只讲优点不讲失效边界 | 读者会在不该用的地方用 |
| 把某一实现当成原理 | 换个框架就不成立 |
| 用类比代替机制 | 类比是入口，不是终点 |
| 堆公式但不解释每个符号的含义 | 数学不是装饰 |
| 开场现象不反直觉 | 这章没有存在价值 |
