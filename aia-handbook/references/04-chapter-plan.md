# 阶段 3 · 章纲

> 目标：给每一章写一份**写手不需要再问任何问题**的任务书。
> 章纲没写清，写手会自己补设定——补出来的东西一百章里有一百个版本。

## 一、章纲模板

````markdown

chapter: "08"
title: "混合检索"

references: ["06", "11"]
provides:
  concepts: ["C021", "C022"]

difficulty: 3
````

## 二、front-matter 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `chapter` | ✓ | 两位章号，与文件名一致 |
| `title` | ✓ | 不超过 12 字 |
| `requires` | ✓ | 读者必须先读懂的章。没有填空数组 |
| `references` | ✓ | 本章会提到的章，可前向 |
| `provides` | | 本章定义的概念 id 与产出的模块路径 |
| `target_words` | ✓ | 目标汉字数，闸门允许 ±25% |
| `difficulty` | ✓ | 1–5，判据见 SPEC 16.2 |
| `deliverable` | ✓ | 名词，可验收 |
| `project_stage` | | 仅 `spine: capstone` 需要：本章把贯穿项目推进到哪个阶段，供 `project-curve.json` 取用 |

### G4 章纲闸门

章纲不再只有人工自检清单。`plan.py` 会按 genre yaml 的 `plan_required_fields`
逐份校：必填字段是否齐、类型/取值是否合法、章纲数是否等于 `book.yaml` 的
`scale.chapters`、每份是否有非空的「## 与相邻章的边界」段；没有 front-matter 的
章纲会显式报错并从 DAG 排除，不再静默漏章。

字段缺失、类型错、章数不符、无 front-matter → 阻断 `plan.py`（rc=1）；
边界段缺失或为空 → warn。`check.py` 的 G4 把同一份结论写进 JSON。
**章纲是全局调度的输入，这一闸拦的就是「写一章发一章」。**

`provides.modules` 尤其重要：它声明了本章的代码接口，
下游章按这个路径 import，`check.py` 用它校验 import 图 ⊆ 章依赖图。

**必须写到函数签名级，光给路径等于没给：**

```yaml
provides:
  concepts: ["C021"]
  modules:
    - module: src/ch05/search.py
      api: "search(q: str, k: int = 5) -> list[Hit]"
```

原因：并行写作时，下游写手照**章纲的签名**写代码，不照上游的实际代码。
签名不写清，两个写手会各造一个 `Hit` 类，缝合阶段就要动代码而不是动文字。

这份签名同时是**写作波次的草案合同**：上游还没写完时，`dep_brief.py` 会把它标
`[draft]` 放进摘要包，下游就能按篇派活；终稿合同产出后用
`dep_brief.py --book <书目录> --check-signatures` 比对，签名对不上报 C08。
`--strict` 可以关掉草案、只认终稿合同。

## 三、节结构的写法

每节四行，缺一不可：

```
### NN.M 标题
- 要点：这一节讲什么，2–3 个判断，不是话题罗列
- 图/表：`fig-NN-M-slug` 或 `表 NN-M 标题`，没有就写「无」
- 代码：`src/chNN/xxx.py::function`，没有就写「无」
```

**「要点」必须写成判断，不能写成名词。**
「讲 RRF」不是要点；「RRF 比加权求和在尺度不一致时更稳」是要点。

节数由 genre 决定（`practical` 4–6 节）。少于 4 节说明内容不够一章，
多于 6 节说明该拆章。

## 四、依赖声明的粒度

一个常见错误：把「提了一嘴」也标成 `requires`，结果 DAG 变成一张渔网。

| 情况 | 标什么 |
| --- | --- |
| 本章全部内容建立在那章的概念之上 | `requires` |
| 只在某一节用到那章的一个结论 | `requires`（如果不用就讲不通） |
| 本章会提到那章，读者不读也能懂 | `references` |
| 只是名词出现 | 不标 |

**判据：删掉那章，本章还成立吗？** 这个判断只需要 10 秒，但决定并行的成败。

## 五、章纲自检

写完一章纲，用这五条过一遍：

- [ ] 不看正文，只看「本章目标」能知道这章要交付什么
- [ ] 每节的「要点」都是判断句，不是话题
- [ ] 每节都标了图/表或明确写「无」
- [ ] 需要代码的节都给了 `src` 路径
- [ ] 「与相邻章的边界」段存在且非空（G4 会查；`dep-brief/` 要读它）
- [ ] front-matter 必填字段齐备、类型合法，章纲数与 `scale.chapters` 一致
- [ ] 「本章容易写歪的地方」至少写了一条

第五条最值钱。**写不出「容易写歪的地方」，说明你还没想清这章的边界。**

## 六、并行前必须全部写完

章纲要一次性写完所有章，不能写一章发一章。

原因：依赖声明的正确性只有看全图才能判断。写第 3 章时觉得不需要 Ch12，
写到第 12 章才发现第 3 章少标了一条边——那时 Ch03 已经写完并在下游了。

章纲阶段多花两小时，批量阶段少返工两天。
