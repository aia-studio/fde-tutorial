# 阶段 5 · 单章写作（写手作业说明）

> 你负责一章。下面是你需要读的东西、要交付的东西，和不要做的事。

## 一、开工前读这四样（按顺序）

1. `03-style-guide.md` —— 本书宪法。只看「本书的差异」部分，genre 基线已经内置
2. `04-chapter-plans/chNN.md` —— 你的任务书。节结构、图表、代码清单都在这里
3. `dep-brief/chNN.md` —— 上游摘要包。上游章的定义、接口、结论，**不含全文**
4. `chapters/ch01.md`（或第一个根节点章）—— 风格范本。语感、密度、图表用法对齐它

**不要读上游章的全文。** 你拿到的是合同和签名，不是原文。读全文会把你带进别人的叙事节奏，
而且上下文一满，你自己的判断就没了。

## 二、动手顺序：代码 → 图 → 正文

这个顺序不能反。反过来，你会先写出「运行结果是 0.87」再去找能跑出 0.87 的代码。

### 第 1 步：代码

按章纲的代码清单逐个写，放在 `src/chNN/`。

- 能不用第三方库就不用。要用就在 `requirements.txt` 写清
- 文件名体现职责（`retriever.py` 而不是 `utils.py`）
- 函数写类型标注，注释写「为什么这么选」，不写「这行做了什么」
- **真跑一遍**，把真实输出记下来

跑不通就先解决，不要先写正文。正文里那些"输出如下"必须来自真跑。

### 第 2 步：图

源码放 `figures/chNN/*.mmd`，头部两行：

```
%% render: 1600x1000
%% source: self
```

渲染：

```bash
npx -y @mermaid-js/mermaid-cli -i figures/chNN/fig-08-1.mmd \
  -o assets/chNN/fig-08-1.svg -c mermaid.config.json -b transparent
```

渲染后打开看一眼，确认没被截断、没出豆腐块。

### 第 3 步：正文

严格按章纲的节结构写，不改节标题、不增删节。

每节开头第一句回答「这一节解决什么问题」，结尾一句自测。

用书里定义好的标注（白名单见宪法），每节不超过 2 处。

### 第 4 步：合同

写完立刻产出 `.book/contracts/chNN.json`：

```json
{"chapter": "ch08",
 "defines": [{"id": "C021", "zh": "混合检索", "en": "Hybrid Retrieval", "def": "..."}],
 "provides": [{"module": "src/ch08/retriever.py",
               "api": "hybrid_search(q: str, k: int) -> list[Hit]"}],
 "assumes": ["C012 向量空间"],
 "hook": "召回稳了，但答案还是可能错——Ch09 讲怎么给答案加引用"}
```

下游写手只靠这个文件理解你写了什么。**合同写不清楚，下游就一定会理解错。**

## 三、逐段的硬要求

| 段 | 要求 |
| --- | --- |
| 头块 | 五个键齐全：本章解决 / 前置 / 阅读 / 动手 / 交付物 |
| 章首导图 | 必须有渲染好的图，不能只放源码 |
| 场景开场 | ≤10 行，只描述问题不给答案，必须是具体的人 |
| 正文各节 | 每节 ≥1 图或表或代码块；代码块 ≤30 行 |
| 小结 | 表格形式，最后一行写「这章在全书里的位置」 |
| 练习 | 2–4 题，每题给**可观察**的验收标准 |
| 自查清单 | ≤10 条勾选项，读者能自己判断 |
| 常见坑 | 3–5 条，格式必须是「现象 → 原因 → 怎么办」 |
| 下一章 | 1–2 句，必须指向真实存在的章 |

## 四、交付前自检

```bash
python scripts/check.py --book <书目录> --chapter chNN
```

不过不交。除此之外自己再看三件事：

- [ ] 每个「输出如下」都是真跑出来的，不是想象的
- [ ] 引用的 `src/` 路径都真实存在
- [ ] 新造的术语都登记进了 `glossary.json`，没有给已有概念另起名

## 五、不要做的事

| 不要 | 为什么 |
| --- | --- |
| 改动 `00`–`04` 任何文件 | 那是基线，只读。有冲突就报出来 |
| 写超出本章纲的内容 | 会侵占邻章的领地，统稿时要删 |
| 引用后文的结论 | 读者还没读到，等于剧透且无依据 |
| 用「稍后介绍」开空头支票 | 必须登记进 `promises.jsonl`，否则统稿会阻断 |
| 为了凑字数拆句 | 字数不够是内容不够，不是句子太短 |
| 编造 benchmark 数字 | 宁可写「本机实测约 X ms（环境：…）」 |
| 贴整段完整代码 | 正文只放关键片段，完整代码在 `src/` |

## 六、写到一半发现章纲有问题怎么办

**立刻停，报告，不要自己改。**

章纲是全局调度的输入。你私自改一章的边界，会导致：
- 邻章内容重复（它按原计划也写了这块）
- 依赖图与实际不符（下游按旧合同写的）

报告格式三行：

```
章节：Ch08
问题：8.3 的融合策略需要先讲 RRF 的数学，但 RRF 在 Ch05 没定义
影响：本章会超字数 1500，或需要把 RRF 上提到 Ch05
建议：把 RRF 定义移到 Ch05 的 5.4，本章只引用
```

由上游决定改章纲还是改书。**写手没有改结构的权限，这是并行能成立的代价。**
