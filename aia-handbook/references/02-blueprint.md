# 阶段 1 · 蓝图

> 目标：把定位变成可调度的结构——篇 → 章 → 依赖图。
> **目录不只是内容结构，还是调度结构。** 这一阶段选错，后面并行会把它放大成灾难。

## 一、先出篇级大纲 `01-outline.md`

3–9 篇，每篇一句话说清「这一篇解决什么」。超过 9 篇说明分类维度混了。

```markdown
## 第 1 篇 基础
解决：读者连环境都跑不起来，讲什么都是空的。
包含章节：Ch01–Ch04

## 第 2 篇 核心能力
解决：能独立搭出一条完整链路。
包含章节：Ch05–Ch12
```

判据：**每篇的「解决」必须是读者的问题，不是内容分类。**
「讲 RAG 相关内容」不合格，「能搭出可用的检索链路」合格。

## 二、再出章级目录 `02-toc.md`

每章一行，五个字段：

```markdown
| 章 | 标题 | 一句话目标 | 字数 | 难度 | 交付物 |
| --- | --- | --- | --- | --- | --- |
| 01 | 从零跑通一条链路 | 半小时内让问题进、答案出 | 5000 | 2 | 能返回答案的最小服务 |
| 02 | 接上真实数据 | 把 csv 换成只读从库 | 5500 | 3 | 数据接入脚本 |
```

- **一句话目标**：动词开头，读者视角。写不出说明这章没有独立价值，合并掉
- **字数**：上下浮动用 `target_words`，允许 ±25%
- **难度**：1–5，判据见 SPEC 16.2。首章 ≤2
- **交付物**：名词，能被验收

## 三、标依赖

依赖写在章纲 front-matter，**不在这里画图**。规则只有三条：

| 边 | 什么时候用 |
| --- | --- |
| `requires` | 读者必须先读懂那一章，本章才讲得下去 |
| `references` | 本章会提到那一章，但不依赖它的内容 |
| 都不用 | 只是名词出现，没有义务 |

**判断标准：删掉那一章，本章还成立吗？** 成立用 `references`，不成立用 `requires`。

两条硬约束：

1. `requires` 不许指向更大的章号（前向依赖）。要指就降级成 `references`
2. 允许前向引用（「详见 Ch08」），不允许前向依赖（读者必须先读过 Ch08）

## 四、编图并看四个指标

```bash
python scripts/plan.py --book <书目录>
```

产出 `.book/dag.json`、`.book/waves.json` 与一份指标报告：

| 指标 | 含义 | 阈值 | 超了怎么办 |
| --- | --- | --- | --- |
| 关键路径 | 最短工期（波数） | ≤ 8 | 放宽 `requires`，把串行链拆成并行支 |
| 最大波宽 | 并发峰值 | 与 `concurrency` 匹配 | 波宽远大于并发上限 → 目录失衡，考虑拆书 |
| 最大扇出 | 被依赖最多的章 | ≤ ⅓ 章数 | 该章拆开，或提到最前面先写 |
| 孤立节点 | 无任何边的章 | 0 | 它其实是一篇独立文章，删掉或并入别章 |

**最大扇出是最容易被忽略的一个。** 被 15 章依赖的第 3 章，一旦写歪，
15 章都要返工。这种章要么拆，要么写到无可挑剔。

### plan.py 另外产出的两张表与 G4 章纲闸门

`plan.py` 除依赖图与指标外，同时写 `.book/writing-waves.json` 与 `.book/project-curve.json`：

- `writing-waves.json`：按 `01-outline.md` 的篇或 `concurrency` 切分的**写作波次**，只用于派活，
  不改变闸门顺序，也不改变装配顺序。别和 `waves.json` 的依赖波次混为一谈。
- `project-curve.json`：仅 `spine: capstone` 的书产出，取章纲 front-matter 的
  `project_stage` 串成项目推进曲线；章纲没写 `project_stage` 时脚本显式打印「已跳过」，
  不冒充通过。`check.py` 的 S24 会在连续 ≥3 章 stage 不推进时给 warn。

`plan.py` 还带一道 **G4 章纲闸门**：按 genre 的 `plan_required_fields` 校验章纲
front-matter 的必填字段与类型、章纲数是否等于 `book.yaml` 的 `scale.chapters`，
并要求每章有非空的「## 与相邻章的边界」段。缺字段、类型错、章数不符、章纲根本没有
front-matter 都会阻断 `plan.py`（rc=1）；边界段缺失只给 warn。`check.py` 的 G4 把同一份
结论写进 JSON，装配前就能看到。

## 五、环的问题其实不存在

真实目录看起来一定有环（讲检索时提评测，讲评测时又用检索举例）。
但因为「`requires` 只能指向更小的章号」，**环在结构上不可能出现**——
任何回路都会先被判成前向依赖。

所以处理方式很简单：被指的那个方向改成 `references` 即可。

```
✗ ch05 requires [08]   → 前向依赖，plan.py 直接失败
✓ ch05 references [08] → 允许，正文写「详见 Ch08」
```

`plan.py` 里保留了环检测，但那是防御性代码，防的是将来放开顺序约束。
现在跑不出来是设计使然。

**代价**：不能表达「Ch07 依赖 Ch09 的结论」。真需要时用 `references`，
读者跳读也不会断——这本来就是更稳的写法。

## 六、产出与验收

```
01-outline.md              篇级大纲
02-toc.md                  章级目录（含五个字段）
04-chapter-plans/chNN.md   章纲（含依赖声明与边界段）
.book/dag.json             依赖图 + G4 结论
.book/waves.json           阅读波次（闸门 / 装配顺序）
.book/writing-waves.json   写作波次（只用于派活）
.book/project-curve.json   项目推进曲线（仅 capstone，章纲写 project_stage 时）
```

- [ ] 篇数 ∈ [3, 9]，每篇的「解决」是读者问题
- [ ] 每章都有动词开头的一句话目标
- [ ] 每章都有可验收的交付物（名词）
- [ ] 关键路径 ≤ 8，最大扇出 ≤ ⅓ 章数，孤立节点 = 0
- [ ] `dag.json` 无环
- [ ] 首章难度 ≤ 2
- [ ] G4 章纲闸门通过：字段齐备、章纲数 == `scale.chapters`、每章有边界段
- [ ] `plan.py` 未打印「项目推进曲线已跳过」（capstone 书必须声明 `project_stage`）

## 七、这一阶段最常见的三个错

| 错 | 后果 |
| --- | --- |
| 按「技术点」排章，不管依赖 | 关键路径拉到 20 波，并行等于没有 |
| 每章都想写得很大（8000 字） | 一半章节靠注水撑到字数 |
| 目录写完不做 DAG 检查 | 写到第 15 章才发现前 5 章都得改 |
